# The Throughline Practice

*Learn in cycles. Move in a line.*

A practice of continuous inquiry and forward flow.

Throughline is a learning log for an organization: one ordered record of what it
intended, what happened, what that taught, and what changed because of it.

Not a method, and not a project-management framework. "Method" implies follow
these steps. "Framework" implies here are the structures. "Project management"
implies control the project. What follows is a way of engaging with work over
time: observe, try something, learn, adjust, continue.

Medicine is a practice. Science is a practice. You get better at one by doing
it, and you never complete it. Real product work has no clean beginning and end
either, so this does not pretend to manage a thing that terminates.

## 1. The business is a line

Most systems organize work by state: backlog, ready, doing, blocked, done,
someday, version two, post-launch. Each is a place work can sit, and several of
them quietly mean *not now*.

Throughline organizes by **sequence**. Every meaningful intention, event,
artifact, decision, exclusion and outcome occupies a position in one ordered
learning log running from past, through Now, into the future.

<!-- diagram: the-line -->
```
PAST           NOW          FUTURE
●───●───●───●───│───○───○───○───○▶
```

There is no permanent Done column accumulating hundreds of cards. Completed work,
captured evidence, decisions, call summaries, screenshots, deployments and
discoveries become part of what the organization has learned. Future work sits
ahead of the present, in the order we currently believe it should happen — it
does not need to be divided prematurely into buckets.

The line itself becomes the durable learning record.

## 2. Work is cyclical, but progress is linear

Much of the work is cyclical. We plan, do, study, adjust, and go again. That
resembles Deming's PDSA cycle and many other iterative models.

```
        PLAN
    ↗            ↘
ADJUST              DO
    ↖            ↙
       STUDY
```

But progress does not literally travel in circles. Time moves forward, so the
cycle unrolls onto the line:

```
TIME ──────────────────────────────────────────────────▶

 Plan → Do → Study → Adjust → Plan → Do → Study → Adjust
 └────────── cycle 1 ────────┘ └────────── cycle 2 ─────
```

The practice is iterative without the structure itself being cyclical. Every
experiment, decision, adjustment, release, mistake and discovery becomes another
point on the line.

**The loop is how we learn. The line is how we move.**

That tension is the mark: the curve is Inquiry, the arrow is Flow, and neither
dominates the other.

## 3. The sliding window

Nobody needs to think about the entire history and future of the line at once.
Attention operates as a window over the line, and it moves forward as work
progresses.

<!-- diagram: sliding-window -->
```
●─┌●─●─●─│─○─○─○─○─○┐▶
        the window moves forward
```

Early on the window holds exploration and foundational work. Later,
implementation. Later still, deployment, observation, refinement, or another
round of discovery. The line was never reorganized. Our attention moved.

This is the natural answer to something other systems reach for milestones,
sprints, archived cards and proliferating columns to express.

## 4. Any slice tells a story

Because work stays ordered, any section of the line can be inspected on its own.

<!-- diagram: selected-slice -->
```
●─┌●─●─●┐─●─│─○─○▶
     a slice answers: what happened here?
```

Look backward and a slice answers *what happened during this period*. Look
forward and it answers *what do we currently expect*. Look around the present
and it answers *where are we, how did we get here, and what comes next*.

So the line is simultaneously the plan, the working queue, the evidence trail,
and the historical record. Those are views over the learning log, not separate
systems.

## 5. Strict ordering

Work has an explicit linear order: A → B → C → D → E.

That does not mean every item depends on the one before it. It means the team has
made an explicit statement:

> Given what we know now, this is the order in which we intend to address the
> work.

That order changes as we learn. **Changing it is not a failure of planning. It is
planning.** What matters is that at any moment the line expresses a coherent
ordering rather than an assortment of loosely prioritized buckets.

## 6. Hierarchy exists, but should be rare

Sometimes one piece of work genuinely consists of parts that must all be
completed together. Then hierarchy helps:

```
Build account recovery
├── Generate recovery token
├── Send recovery email
├── Reset-password interface
└── Expire used token
```

But hierarchy should mean something stronger than "these things seem related."
The parent is *one unit of work* whose constituent parts must collectively be
done. If the children can meaningfully be prioritized, delivered, deferred or
evaluated independently, they belong directly on the line:

```
──── A ─── C ─── other work ─── B ─── E ─── D ───▶
```

Deep task trees create an attractive fiction that the shape of the work is known
in advance. The line encourages decomposition only when decomposition helps us do
the work.

## 7. Avoid temporal buckets

Boards accumulate places that effectively mean *not now*: blocked, post-go-live,
version two, later, someday. Linear ordering offers another answer.

**If something should happen later, put it later.**

<!-- diagram: landmark-not-bucket -->
```
●───●───│───○───○───◆───○───○▶
                    └─ work after launch is a PLACE,
                       not a bucket
```

"Post-launch" does not need to be a container. It can simply describe where the
work sits relative to a landmark. Likewise a blocked item does not require a
permanent region of the workflow; its position and a note communicate what
matters without creating another destination where work disappears.

## 8. History is first-class

A board is excellent at answering *what state is work in right now*. It is worse
at answering *what did this look like six months ago* — eventually the Done
column is archived away.

<!-- diagram: history-months -->
```
JAN FEB MAR     APR MAY
●───●───●───│───○───○▶
```

**Old work isn't clutter. It's farther away.**

Zoom out to understand the line. Zoom in to understand a period. Move backward
to investigate history. Move forward to inspect the plan. Return to Now to work.

## 9. Planning is progressive

The future should become less detailed as distance from the present increases.

```
NOW                                              FUTURE
 │
 ▼
████ ███ ███ ██   ── ▓▓▓ ▓▓▓ ──── ▒▒▒▒▒ ─────── ░░░░░░░
high detail          moderate detail        low detail
```

Near-term work can be concrete because we know more about it. Far-future work
should stay coarse, because pretending otherwise manufactures certainty that does
not exist. As the window moves, distant ideas approach and are progressively
explored, decomposed, reordered, clarified — or discarded.

Rolling-wave planning becomes a property of the representation rather than a
separate ceremony.

## 10. The core model

The whole thing stays small. Conceptually we need:

1. **A line** — the learning log ordered through time
2. **Entries** — intentions, events, evidence and outcomes worth preserving
3. **A Now position** — the boundary between history and intention
4. **A window** — the portion currently receiving attention
5. **Limited hierarchy** — decomposition where the pieces genuinely form one whole
6. **Lightweight metadata** — enough to describe exceptional conditions without
   turning those conditions into places where work lives

Everything else has to justify its existence.

## 11. Status is position

"Done" is not a state. It is a location: **behind Now**.

```
        BEFORE                              AFTER

           NOW                                 NOW
            │                                   │
 ──●──●─────│──○──○──○──▶            ──●──●──●──│──○──○──▶
                ↑                           ↑
          parse line.md                parse line.md
                                    same item — now history
```

Completing something means moving it behind Now, which records that it happened
before everything still ahead. There is no completion flag that can drift out of
sync with the ordering, because completion *is* the ordering.

Finishing work out of order is expressed the same way: move it behind Now. The
line therefore stays a true chronological record rather than a plan with
scattered checkmarks.

## 12. Markers are landmarks

`Deploy`, `v0.1`, `Cycle 2` are zero-width entries occupying positions on the
line — not containers.

<!-- diagram: markers-after-launch -->
```
●───●───│───○───○───◆───○───○▶
                    └─ work after launch is a PLACE,
                       not a bucket
```

There is nowhere to put work, only a place to put it. That is the difference.

## 13. The Window is a view

Now is stored. The window is derived from wherever you happen to be looking.

<!-- diagram: window-is-a-view -->
```
reviewing March:
┌●─●─●┐─●─●─●─│─○─○─○─○▶

planning Q3:
●─●─●─●─●─●─│─○─┌○─○─○┐▶

     one line, two readers, no copies
```

This is what makes "any slice tells a story" free rather than a feature. Two
people looking at different spans are looking at the same data.

## 14. Inquiry

The unit of progress is not a completed task or a decision made. It is
something learned and carried forward.

Each pass asks the same five questions:

1. What do we know?
2. What do we need to learn?
3. What should we try next?
4. What happened?
5. **What does that change?**

```
   QUESTION
      ↓
 ┌──────────┐
 │   TRY    │
 │     ↓    │
 │ OBSERVE  │
 │     ↓    │
 │  LEARN   │
 └────┬─────┘
      │
      └──────────────────────▶  and the line ahead is different
                    NEXT
```

The fifth question is the one that moves things, and its answer is *a changed
line* — not a stored sentence. You answer it by reordering, adding, or dropping
work ahead of Now. An answer that changes nothing was not worth asking.

## 15. Accountability is learning carried forward

Throughline does not ask whether reality matched the plan. It asks whether the
organization converted reality into learning, and learning into action.

That is a different form of accountability. It is not a scorecard for whether a
person or team delivered what they said they would deliver. A plan is a snapshot
of what the organization believed at the time, not a promise that future reality
must obey. Good work may ship the planned thing, but it may also invalidate an
assumption, expose a constraint, explain why something should be excluded, or
make the next decision better informed.

Accountability means carrying learning forward until it changes what the
organization does.

That creates two responsibilities:

1. **Advance knowledge.** Discover something true, useful, or clarifying.
2. **Operationalize knowledge.** Let that discovery change the line, the
   product, the decision, the customer conversation, the process, or the next
   experiment.

Learning without action becomes archive dust. Action without learning becomes
churn. The practice is the loop between them.

## 16. Accounting for the line

As the line grows, some things need to be accounted for.

An intention is accounted for when the organization can say what happened to it:
it shipped, it taught us something, it was intentionally excluded, it was
superseded, it was invalidated, or it remains an open thread.

An event is accounted for when the organization can say what it meant: what it
taught us, what changed because of it, or why nothing should change.

This is reconciliation in the sense of sensemaking, not blame. The useful
categories are narrative categories:

- **reflected** — the intention appears in the outcome;
- **evidenced** — the claim is supported by an artifact, observation, test,
  screenshot, call summary, whiteboard photo or release;
- **superseded** — a later decision replaced the old intention;
- **intentionally excluded** — the organization chose not to carry it forward,
  with a reason;
- **unconnected** — there is not yet a clear link between intention, event and
  outcome.

The last category is not a failure. It is a place where the story lost
continuity. The right response is not "who missed this?" The right response is
"what did we learn, and what does that change?"

## 17. The central inversion

Kanban asks us to imagine work moving across a board:

```
TODO          DOING       DONE
● ● ●    →     ● ●    →   ● ● ● ● ● ● ● ● ●
```

Throughline asks us to imagine ourselves moving through the work:

```
                              YOU ARE HERE
                                   ↓
 ──────────────────────────────────│──────────────────────────▶
        what happened              │        what might happen
                                  NOW
```

That inversion may be the central idea. Work doesn't move toward Done. **Time
moves us through the work.**

## 18. Using `tlflow`

`tlflow` keeps one learning log in one readable file in your repository. It is a
terminal UI and a command line at once, so a person and a coding agent can both
work from the same record.

The screen shows two zoom levels at once — the whole line as a ribbon, and
readable titles for whatever is in the window:

```
┌●─●─│─○─○─◆─○┐▶

  ● sketch the practice  ^k3f
  ● pick the name  ^m2a
> │ NOW
  ○ write docs/method.md  ^q1d
      sixteen diagrams, seven generated
  ○ build the ribbon  ^r7e
  ◆ v0.1
  ○ MCP server  ^t9a

? help · q quit
```

The command line speaks the same vocabulary:

```
$ tlflow advance --result "sixteen diagrams, seven generated by tl itself"
what does that change?  tlflow move · tlflow add · tlflow drop

$ tlflow add "generate the diagrams" --after now
```

Placement is required. There is no backlog to drop things into — choosing where
work goes is the thinking the practice asks for.

`tlflow check` lints a line against the practice: disguised buckets, unsharpened work
inside the window, over-detailed work far from Now, hierarchy that should be on
the line.

## The vocabulary

| term | meaning |
|---|---|
| **Practice** | the whole of it; you get better by doing it and never complete it |
| **the Line** | the learning log ordered through time |
| **Flow** | movement along the Line; one direction, forward |
| **the Window** | the current field of attention |
| **Inquiry** | the learning that decides what comes next |
| **Cycles** | repeated experiments, unrolled onto the Line |
| **Now** | the moving boundary between observation and intention |

> Everything goes on the Line.
> Move it forward on the Line.
> That's outside the current Window.
> Don't create a post-launch bucket. Put it after launch.
> Don't put it in Blocked. Decide where it belongs on the Line.

**Cycles of learning. A line of progress.**
